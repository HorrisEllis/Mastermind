System Architecture
§01

Mastermind is a single-page Electron application structured as three files: index-browser.html (UI + CSS), nexus-engine.js (application logic, ~9,300 lines), and mastermind-foundation.js (bedrock layer: registry, vault, tags, events). A fourth file, mastermind-siso-jaa.js, provides the SISO stream runtime and JAA delta ledger — loaded first before any other script.

/* Load order — strict */ mastermind-siso-jaa.js ← FIRST · SISO stream + JAA gates + MM_BUS + MM_RUNNER mastermind-foundation.js ← SECOND · MMRegistry, MMVault, MMLog, MMTags, MMDomains nexus-engine.js ← THIRD · all modules, canvas, auth, UI
MASTERMIND-SISO-JAA.JS
Pure functional event pipeline. SISOEvent, SISOGate, SISOStream, SISOStreamLog. JAAPureGate, JAAStateGate, JAAMutationBatch, JAAReadSet. JAAMemoryStore (SHA-256 content-addressed), JAAMemoryRefs (name→hash). JAARunner (resolve reads → apply mutations). MMEventBus (live SISO-backed pub/sub). Global instances: MM_BUS, MM_RUNNER.
Size: ~600 lines · No dependencies
MASTERMIND-FOUNDATION.JS
Bedrock layer. MMRegistry (UUID entity ledger), MMDelta (immutable change history), MMTags (6-category tag system), MMDomains (400+ taxonomy), MMVault (AES-256-GCM encrypted storage), MMLog (structured ring-buffer logger), MMRipple (event bus), MMDiag (diagnostic runner), MMToast (toast coordinator), MMTagsUI (pill renderer).
Size: 1,827 lines · Globals: 10
NEXUS-ENGINE.JS
All application logic. Canvas (infinite pan/zoom, 18 node types, connections, force layout), Auth (PBKDF2+AES-256-GCM+RSA-OAEP), Startup flow (watchdog, vault gates), Brain Map V2 (3D sphere, 13 meta-domains), Spatial Void + Creative (merged), Horizon Living, ALM, Options, AI (Anthropic/OpenAI/Ollama/LM Studio), Import (5 formats), Toast system (48 named toasts).
Size: ~9,300 lines · Functions: 300+
SISO + JAA Framework
§02

SISO (Stream In, Stream Out) enforces pure functional event-driven architecture. Every operation is an immutable event flowing through gates. JAA (Jaa-main) extends SISO with PureGate/StateGate distinction, content-addressed storage, and the Runner pattern for stateful mutations.

// Core primitives const event = new SISOEvent('mm.void.seed.add', { text: 'my idea' }); // Pure gate — no side effects, transforms event → event class MySeedGate extends JAAPureGate { process(event) { return new SISOEvent('mm.void.seed.ready', { ...event.data, id: uuid() }); } } // Event bus — subscribe to any event type MM_BUS.on('mm.void.seed.add', (data) => console.log(data)); MM_BUS.emit('mm.void.seed.add', { text: 'my idea' }); // Observe all events MM_BUS.sampleLog(); // → { level, count, entries } MM_RUNNER.sample(); // → { pending, eventCount, gateCount }

Vault Architecture — Filesystem Only
§02.5

MASTERMIND uses filesystem vault only. There is no browser-only mode. localStorage is a session-speed cache — never the primary store. Every save goes to mastermind.vault on disk via Electron IPC.

/* Storage hierarchy */ PRIMARY: {dataDir}/mastermind.vault ← AES-256-GCM encrypted, atomic write (.tmp → rename) CACHE: localStorage['nexus_mm_v3'] ← session speed cache, rebuilt from vault on load SESSION: localStorage keys ← auth meta, features, opts, AI config (settings only) /* Vault creation flow */ setupCreateVault() → requires window.NXAPI ← hard gate: desktop app only → NXAPI.defaultFolder() ← ~/Documents/MASTERMIND/ if no folder set → NXAPI.vaultWrite(path, json) ← writes initial vault structure → NXAPI.vaultExists(path) ← watchdog confirms file on disk → NX_CONFIG.vaultPath = path ← stored for all subsequent reads/writes → proceed to ss-keygen ← only if vault write succeeded /* Save flow */ vaultSave(showToast) → if (!NXAPI): warn + localStorage cache + return → vaultSerialize() → JSON string → AUTH.key ? _aesEncrypt() : plain JSON → NXAPI.vaultWrite(vaultPath, payload) ← atomic: .tmp → rename → localStorage cache update → every 10 saves: NXAPI.vaultBackup() /* Load flow */ loadCanvas() → NXAPI.vaultRead(vaultPath) ← primary source of truth → AUTH.key ? _aesDecrypt() : plain parse → localStorage cache update → fallback to localStorage cache if vault empty (first launch)

Vault Gate System
§03

Nothing works unless the vault exists and is valid. Three sequential gates block all entry. The startup watchdog runs before login is shown for returning users. The login gates run before password derivation. The folder gate runs on first-time setup.

GATE 0 · STARTUP WATCHDOG
When: On startupRoute() for any user with a configured data dir.

Check: _vaultWatchdogCheck() — reads vault file from disk, parses JSON, confirms file exists post-read.

Fail: _showVaultMissingScreen() — blocks ALL routing. Shows 3 recovery options: Recreate, New Folder, Restore from Backup.

Pass: _continueStartup() — proceeds to login or home.
Function: _vaultWatchdogCheck() · SISO: mm.vault.missing
GATE 1 · LOGIN IDENTITY
When: On loginSubmit() before any cryptographic work.

Check: _authLoadMeta() must return a valid identity object (username, salt).

Fail: "No identity found — complete first-time setup." Inline error + toast + MMLog.error + SISO mm.auth.login.fail.
Blocks: password derivation, vault access, app entry
GATE 2 · VAULT KEYS
When: After Gate 1 passes, before key derivation.

Check: localStorage.getItem(AUTH_VAULT_KEY) must be non-null (encrypted private key + public key bundle).

Fail: "Vault keys missing — vault may be corrupted." + SISO mm.auth.login.fail { reason: 'no_vault_keys' }.
localStorage key: nexus_auth_vault
GATE 3 · VAULT FILE ON DISK
When: Electron only, after Gates 1+2 pass.

Check: NXAPI.vaultExists(dataDir + '/mastermind.vault') must be true.

Fail: "Vault file not found on disk." + auto-shows vault missing screen after 1.2s + SISO mm.auth.login.fail { reason: 'no_vault_file' }.

Pass: Opens vault file on disk, stores NX_CONFIG.vaultPath, proceeds.
Electron only · Emits: mm.vault.confirmed

VAULT MISSING RECOVERY SCREEN

When _showVaultMissingScreen() is called, it overrides all routing and renders a recovery UI with three options. The screen persists until a vault is confirmed. Every recovery action emits a SISO event for observability.

ActionFunctionWhat It Does
RECREATE VAULT_vaultRecreate()Writes a fresh mastermind.vault to current dataDir. Re-runs startupRoute() on success.
CHOOSE NEW FOLDERpickStartupFolder()Opens folder picker dialog. User selects a folder containing an existing vault.
RESTORE FROM BACKUP_vaultRestoreFromBackup()Opens file picker. Validates JSON. Writes to dataDir/mastermind.vault. Restarts.

Encryption Spec
§11
Algorithm: AES-256-GCM (256-bit key, 96-bit IV, 128-bit auth tag) Key derivation: PBKDF2-SHA256 · 310,000 iterations · 256-bit random salt Key storage: Derived key NEVER stored — re-derived from password each session RSA key pair: RSA-OAEP · 2048-bit · SHA-256 hash Public key: SPKI format · base64 stored unencrypted in nexus_auth_vault Private key: PKCS8 · encrypted with AES key · stored as { iv, data } PIN auth: SHA-256(pin + username) → read-only session, no decryption access Vault gate: AES-GCM round-trip test before app entry (featuresConfirm) Atomic writes: Write to .tmp → rename (NTFS atomic via Electron IPC)
