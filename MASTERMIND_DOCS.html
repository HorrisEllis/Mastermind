System Architecture
§01

Mastermind is an Electron application mid-way through a deliberate de-monolithing. Two large files remain (index-browser.html — all UI + CSS; nexus-engine.js — the un-extracted remainder), while everything bedrock lives under foundation/ and everything feature-shaped lives under modules/. Twenty-four scripts load in a strict order; the order is not cosmetic, it encodes dependency direction.

/* Real load order — read straight out of index-browser.html */ foundation/siso-jaa/mastermind-siso-jaa.js ← SISO stream, JAA gates, MM_BUS, MM_RUNNER foundation/bus/event-ledger.js ← ring buffer over BOTH buses (must precede emitters) foundation/core/mastermind-foundation.js ← MMRegistry, MMDelta, MMTags, MMDomains, MMLog… nexus-canvas.js ← canvas engine + global error/hit-test capture foundation/theme/mastermind-bg.js foundation/ui/mm-dialogs.js ← mmPrompt / mmConfirm (window.prompt is unusable here) foundation/vault/mastermind-vault.js foundation/ai/clearglass-transport.js nexus-engine.js ← the remaining monolith modules/alm/{engine,ui,events}.js foundation/bus/{warp-core,mastermind-warp-spine}.js modules/leverage-map/{engine,events,ui}.js modules/voice-lattice/engine.js ← association / friction / predictive engines modules/pattern-engine/engine.js modules/lattice/lattice.js ← universal substrate modules/lattice/coherence.js ← ripple / contradiction / incoherence modules/voice-lattice/{dictation,recall,speech}.js

Two buses exist and this matters. The global MM_BUS is SISO's (from mastermind-siso-jaa.js); foundation exposes its own separate bus as _MM_BUS. Different implementations, different events. The event ledger taps both and tags each entry with its origin — anything assuming a single bus will silently miss half the traffic.

SISO + JAA Framework
§02

SISO (Stream In, Stream Out) enforces pure functional event-driven architecture. Every operation is an immutable event flowing through gates. JAA (Jaa-main) extends SISO with PureGate/StateGate distinction, content-addressed storage, and the Runner pattern for stateful mutations.

// Core primitives const event = new SISOEvent('mm.void.seed.add', { text: 'my idea' }); // Pure gate — no side effects, transforms event → event class MySeedGate extends JAAPureGate { process(event) { return new SISOEvent('mm.void.seed.ready', { ...event.data, id: uuid() }); } } // Event bus — subscribe to any event type MM_BUS.on('mm.void.seed.add', (data) => console.log(data)); MM_BUS.emit('mm.void.seed.add', { text: 'my idea' }); // Observe all events MM_BUS.sampleLog(); // → { level, count, entries } MM_RUNNER.sample(); // → { pending, eventCount, gateCount }

Vault Architecture — Filesystem Only
§02.5

MASTERMIND uses filesystem vault only. There is no browser-only mode. localStorage is a session-speed cache — never the primary store. Every save goes to mastermind.vault on disk via Electron IPC.

/* Storage hierarchy */ PRIMARY: {dataDir}/mastermind.vault ← AES-256-GCM encrypted, atomic write (.tmp → rename) CACHE: localStorage['nexus_mm_v3'] ← session speed cache, rebuilt from vault on load SESSION: localStorage keys ← auth meta, features, opts, AI config (settings only) /* Vault creation flow */ setupCreateVault() → requires window.NXAPI ← hard gate: desktop app only → NXAPI.defaultFolder() ← ~/Documents/MASTERMIND/ if no folder set → NXAPI.vaultWrite(path, json) ← writes initial vault structure → NXAPI.vaultExists(path) ← watchdog confirms file on disk → NX_CONFIG.vaultPath = path ← stored for all subsequent reads/writes → proceed to ss-keygen ← only if vault write succeeded /* Save flow */ vaultSave(showToast) → if (!NXAPI): warn + localStorage cache + return → vaultSerialize() → JSON string → AUTH.key ? _aesEncrypt() : plain JSON → NXAPI.vaultWrite(vaultPath, payload) ← atomic: .tmp → rename → localStorage cache update → every 10 saves: NXAPI.vaultBackup() /* Load flow */ loadCanvas() → NXAPI.vaultRead(vaultPath) ← primary source of truth → AUTH.key ? _aesDecrypt() : plain parse → localStorage cache update → fallback to localStorage cache if vault empty (first launch)

Vault Gate System
§03

Nothing works unless the vault exists and is valid. Three sequential gates block all entry. The startup watchdog runs before login is shown for returning users. The login gates run before password derivation. The folder gate runs on first-time setup.

GATE 0 · STARTUP WATCHDOG
When: On startupRoute() for any user with a configured data dir.

Check: _vaultWatchdogCheck() — reads vault file from disk, parses JSON, confirms file exists post-read.

Fail: _showVaultMissingScreen() — blocks ALL routing. Shows 3 recovery options: Recreate, New Folder, Restore from Backup.

Pass: _continueStartup() — proceeds to login or home.
Function: _vaultWatchdogCheck() · SISO: mm.vault.missing
GATE 1 · LOGIN IDENTITY
When: On loginSubmit() before any cryptographic work.

Check: _authLoadMeta() must return a valid identity object (username, salt).

Fail: "No identity found — complete first-time setup." Inline error + toast + MMLog.error + SISO mm.auth.login.fail.
Blocks: password derivation, vault access, app entry
GATE 2 · VAULT KEYS
When: After Gate 1 passes, before key derivation.

Check: localStorage.getItem(AUTH_VAULT_KEY) must be non-null (encrypted private key + public key bundle).

Fail: "Vault keys missing — vault may be corrupted." + SISO mm.auth.login.fail { reason: 'no_vault_keys' }.
localStorage key: nexus_auth_vault
GATE 3 · VAULT FILE ON DISK
When: Electron only, after Gates 1+2 pass.

Check: NXAPI.vaultExists(dataDir + '/mastermind.vault') must be true.

Fail: "Vault file not found on disk." + auto-shows vault missing screen after 1.2s + SISO mm.auth.login.fail { reason: 'no_vault_file' }.

Pass: Opens vault file on disk, stores NX_CONFIG.vaultPath, proceeds.
Electron only · Emits: mm.vault.confirmed

VAULT MISSING RECOVERY SCREEN

When _showVaultMissingScreen() is called, it overrides all routing and renders a recovery UI with three options. The screen persists until a vault is confirmed. Every recovery action emits a SISO event for observability.

Associative Lattice
§16

One substrate every module feeds. Anything entering it is automatically tagged, linked to whatever came before with an inferred relation, and linked to earlier items by vocabulary overlap and shared tags. Nothing about this is manual — the explicit versions of these actions still exist, this is what happens without asking.

Edge typeMeaning
sequenceConnected to the previous entry, labelled with the inferred relation
associationJaccard overlap on content words ≥ 0.12
shared-tagSame distinctive tag within a 120-node lookback

Relations (heuristic, not comprehension): opens · elaborates (same kind, strong overlap) · returns to (strong overlap after a >30min gap) · crosses into (different kind, related topic) · shifts to (little overlap).

Coherence Engine
§17

Runs automatically on every lattice ingest. Findings write into ALM's delta log, so they become part of the growth record rather than a toast you missed.

FindingTrigger
RIPPLEWhat you wrote touches a Horizon seed or commitment — names the plan
CONTRADICTIONSame subject, opposite polarity, ≥ 0.22 topical overlap
INCOHERENCEConflicts with a commitment you actually made — held separate, heavier

Honest limits. Polarity is grammatical-negation counting, not language understanding — it misses sarcasm and conditionals. Semantic negatives (avoid, stop, fail) are deliberately excluded from the negation set: including them made a commitment that merely mentioned avoidance match the polarity of its own violation, and incoherence went undetected. Thresholds are tuned to stay quiet, because a detector that cries wolf gets ignored.

Intelligence types are automatic. cohIntelligenceFromLattice() derives ratings from real lattice activity with a 14-day half-life and syncs them into ALM/DOMAIN_STATE. The Ni/Ne/Ti/Te and INTEL titlebar buttons were removed — they were panels maintained by hand.

Voice: Dictation · Recall · Capture
§18

Dictation is a capability on every field, not a feature in one module. Focus any input, textarea or contenteditable → a mic appears; F2 toggles. Text inserts at the cursor, not appended. Spoken punctuation, new line, new paragraph, and scratch that all work. Everything dictated joins the lattice exactly like typed text.

Rolling recall keeps a trailing 10-minute audio ring and cuts each segment from onset minus 3 seconds — detection always lags the first syllable, so reaching backwards is the only way not to clip it. RMS detection with hysteresis keeps one utterance from fragmenting on every breath. Off by default: an always-on microphone is a deliberate choice, not a quiet default.

dictApplyCommands(raw) // spoken → written, punctuation tidied dictInsertInto(el, text) // cursor-accurate, React-safe value setter recallPrune(chunks, now, windowMs) recallSelectSegment(chunks, onsetTs, prerollMs, endTs) class RecallVAD // push(rms, ts) → 'start' | 'end' | null

Testing honesty. No microphone or SpeechRecognition exists in the build environment. The pure logic — command substitution, cursor insertion across three field types, ring pruning, pre-roll selection, VAD hysteresis — is genuinely tested. The hardware wiring is not, and is flagged as such wherever it appears.

Web AI Agents
§19

ChatGPT, Claude, Perplexity and Gemini run inside Mastermind's own Electron process (foundation/ai/clearglass-main.js). No separate app, no userscript manager, no external browser. Each agent gets its own BrowserWindow; each account gets its own session partition (persist:cg-<agent>-<accountId>), so multiple logins for one provider never collide.

BehaviourWhy
backgroundThrottling: falseNecessary but not sufficient. Stops Chromium throttling a hidden window's timers — but a window built with show:false and never shown also reports document.hidden === true to its own page permanently, independent of timer throttling. Sites can legitimately defer streaming/render work while they believe they're backgrounded. Fixed in §20 by keeping windows OS-realized ("parked" off-display) instead of ever leaving them unshown.
Fresh conversation per askOtherwise every ask piles into one chat and later prompts are answered by a model that read the earlier ones
Strict login probeURL on the agent's host + not a login path + visible composer. Any-composer counting reported "signed in" on a Google sign-in page
Serial per accountOne chat tab is inherently sequential; different agents/accounts run in parallel
Named failuresNO_COMPOSER · SEND_NEVER_STARTED · TEXT_INJECTION_FAILED · TIMEOUT_WAITING_REPLY — never a silent hang

Model selection stays in each agent's own UI — native picker, always current, nothing to keep in sync. The default checkbox in Options → AI sets provider and account together, so the panel and the routing cannot disagree.

Selector honesty: Claude and ChatGPT are confirmed against the live sites. Perplexity and Gemini are best-known guesses and say so in the UI.

WHY THE TEST BUTTON HUNG UNTIL YOU OPENED THE WINDOW

A BrowserWindow built with show:false and never actually shown reports document.hidden === true / visibilityState === 'hidden' to its own page — permanently, not just until the next paint. This is the Page Visibility API, a completely separate mechanism from Chromium's timer throttling. backgroundThrottling:false (§19, the original fix attempt) only stops timers from being throttled while occluded; it does nothing for Page Visibility. ChatGPT and Claude's own client code can legitimately defer streaming or DOM-commit work while their page believes it's backgrounded — independent of any Electron-level setting. Opening the window from the toast flipped Page Visibility to 'visible' and the deferred work proceeded. That was the entire symptom.

THE FIX — PARKED, NOT HIDDEN

Agent windows now stay OS-realized at all times. Instead of show:false + .hide(), a window not meant to be seen is parked: moved off-display (x:-32000, y:-32000), skipTaskbar:true, shown via showInactive() so it's Chromium-visible without ever appearing to a person or stealing OS focus. Revealed means on-screen, in the taskbar, focused — only true while someone is signing in or looking at Show/Open. Every former .hide() call site (window close, sign-in-detected, the cg:hide IPC handler) now parks instead, because hiding flips Page Visibility back to hidden and would silently reintroduce the exact bug.

_cgPark(w) // off-display + skipTaskbar + showInactive() — OS-visible, person-invisible _cgReveal(w) // on-screen + taskbar + show() + focus() — for sign-in / Show

Configuration for the window/timing constants and all four agent definitions moved to foundation/ai/clearglass-config.js — one file, named IDs (PARKED / REVEALED / CLOSED), a comment block for adding a fifth agent. Verified byte-identical to what was previously scattered inline before the move, not reconstructed from memory.

MEMORY ARCHITECTURE — COMPARTMENTS (NEW MODULE)

New modules/memory/ — a generic compartment system (mode / system / domain / project / person / custom, or anything else worth naming), each holding pointers into stores that already exist (lattice nodes, canvas nodes, ALM entries, voice utterances) rather than duplicating content. Deliberately asymmetric by design: depth/spatial position is automatic (recency-weighted, real shared-content overlap drives the force layout — the same principle the intelligence-type sync above uses), but a compartment's existence, name, and contents are always a direct action — creation, assignment, and removal are never inferred or silent, only suggested. The one place in this session's automation push where "automatic by default" was deliberately NOT the answer, because the container someone chooses to think inside is a different kind of thing than self-knowledge computed from their activity.

Visualized as a pseudo-3D force-directed canvas (real <canvas> 2D, depth simulated via scale/opacity/mouse-parallax) — the same proven technique Brain Map's own #brain-cvs already uses, not a new WebGL dependency. SECURE VAULT WIPE

Options → Data & Storage → Danger Zone now has two tiers. Wipe Vault (existing) is a plain delete — fast, but the file's bytes typically remain on disk, readable, until something else overwrites those exact blocks, sometimes never. Secure Wipe (new) overwrites the vault file — and every .backup.*.json snapshot next to it, since leaving those would defeat the point — with two random passes and a final zero pass, fsync'd after each so a pass actually reaches storage rather than sitting in a write-back cache, then renames to a random name before unlinking (the original filename is metadata too). Both require typing a confirmation phrase; Secure Wipe's is a different, stronger word than the regular wipe's.

Honest limit, stated here and in the confirmation dialog, not hidden: on an SSD, overwrite-in-place is not a physical guarantee. Wear-leveling and TRIM mean the controller can remap "the same" logical file to different physical cells between writes, so the overwrite may never touch the flash cells that held the old data. This is a well-documented limitation of software-level secure-delete on SSDs generally, not specific to this feature. The vault's real protection is that it's AES-256-GCM encrypted in the first place — as long as the password is never recoverable, ciphertext technically still readable somewhere on disk doesn't hand anyone the plaintext. Secure Wipe is defense in depth on top of that encryption, and on a spinning HDD it genuinely does destroy the old data outright — but it is not a substitute for the encryption being sound, and the UI does not claim otherwise.
